## 二、需求编号（从输入文档逐条抽取）

抽取原则：只抽**规范性语句**（"必须/应/只能/不得/不要"以及表格里被定义的行为），叙述性背景不编号。

### A. 产品形态（§一、§五）

- **R01** 最终产品只保留三种结果：已删除 / 待删除可恢复 / 保留。
- **R02** 已删除的条件：在已批准的直接清理类别内；本地检查无保护或使用阻碍；JEV 与 LLM 均明确同意永久删除。动作=删除并完成记账，随后出现在本轮通知与历史清单。
- **R03** 待删除的条件：无明确保留信号；尚不足以永久删除；能够确认在已批准范围内可安全移动。动作=移入隔离区，记录原因和最早清空时间，通知用户。
- **R04** 保留的条件：任一模型明确要求保留；文件受保护、仍被使用、身份变化；移动安全性未知；模型服务失败。动作=原位不动并说明原因；**服务失败必须与"已确认有用"区分**。
- **R05** 边界修正："不确定是否该永久删除"可以进入观察；"连移动是否安全也不确定"必须留在原位。

### B. 观察区与到期（§五）

- **R06** 新进入观察区的普通候选默认 14 天，用户可一次设置为 30 天。
- **R07** 该默认值不追溯、不缩短现有 6 个对象的 30 天保留期。
- **R08** 到期步骤固定三步：①检查是否恢复、被保护、出现新使用信号、文件发生变化、通知没有送达；②仍满足清空条件时再让双模型审核永久删除；③双同意且授权有效才清空，仍不确定就保留并说明原因。
- **R09** "观察期没有收到投诉"≠证明没有依赖；不为此开发全机异常监控；只提供清单、恢复入口、保留操作、到期复查；观察不到的使用情况保留为未知。
- **R10** 首次只需确认一次：管理哪些目录；哪些类别允许直接删除；其它候选观察多久；每轮文件数与空间额度；通知显示在哪里。
- **R11** 扩展名、mtime、双模型同意不能单独把整份 Downloads 变成"全部允许直接删除"；可再生产物要有可检查的来源或生成规则；普通资料依据不足就保留。
- **R12** 日常不再要求逐文件写 JSON、手工算摘要、给每个缓存做备份。

### C. 调整 1（§六）

- **R13** 复用现有 JEV 与 MiniMax 适配器，把审核输出接成三种处理结果。
- **R14** 双方永久删除同意是直接清理的必要条件；任何明确保留意见不得被另一方覆盖。
- **R15** 移除普通垃圾日常使用中的"逐文件人工证明＋完整副本"前提。
- **R16** 改为程序自动取得与类别相关的必要事实。
- **R17** 拿不到事实的对象保留；不让 LLM 编造文件用途、使用历史、引用关系或备份存在性。
- **R18** 这不是改一个开关：判断结果必须实际连到动作，并验证动作语义。

### D. 调整 2（§六）

- **R19** 保留身份复查、私有隔离区、恢复、锁、额度、操作记账、错误收敛。
- **R20** 直接清理：具有明确的永久删除授权与审核，正确记录该次不可撤销动作。
- **R21** 观察清理：安全移动、可恢复、通知、保留期到期复核。
- **R22** 失败或不确定：保留现场，明确显示未执行原因。
- **R23** 不得另写裸 `os.Remove` 旁路；不得篡改旧对象保留期或授予追溯权限"模拟实现"；不重新设计扫描器、数据库基础设施或后台服务。

### E. 调整 3（§六）

- **R24** 每轮生成固定位置的本机结果页或清单，只分三个部分。
- **R25** 三部分各自必须看得到字段：已删除（原路径、大小、删除完成时间、简短理由）；待删除（原路径、大小、移动时间、最早清空时间、简短理由、恢复/保留入口）；保留（原路径、保留原因、是否接口失败或缺依据）。
- **R26** 通知内容形如"本次删除 2 个文件；3 个文件进入待删除区，最早 14 天后清空。查看详情／恢复。"
- **R27** 待删除对象在进入隔离区时让用户获知；永久清空前给简短提醒；通知未送达时先保留；不得把"日志写了"当成已通知。
- **R28** 无需逐项审批低风险文件，也不需要每文件弹窗。
- **R29** 复用 `items + events` 汇总真实结果；只有已完成并确认的动作计入"已删除"；候选、模型意见、intent、debug 模拟数不得计入。
- **R30** 列表超过展示上限时显示总量与"还有多少"。
- **R31** Mac 先做一种系统通知 + 本地详情入口；不引入通用通知平台。

### F. 验收（§七）

- **R32** 样例一：真实双审核同意永久删除 → 一次运行后文件删除，实际完成记录与用户通知一致。
- **R33** 样例二：不确定但可安全移动 → 进入待删除区，路径/原因/最早清空时间清楚，可成功恢复，到期复核能决定清空或继续保留。
- **R34** 样例三：必须保留的文件不动；模型请求失败不产生删除、不误报"清理成功"。
- **R35** 样例四：完成以上验证的那份程序成为定时任务调用的版本；明确配置范围与权限后才解除暂停。
- **R36** 6 个旧隔离对象按原合同继续可恢复，不为新功能改变状态；它们的清空决定单独明确。

## 三、任务拆分

编号 T01–T26。每条给出**交付物**、**完成判据**、**依赖**。T 与 R 的对应关系见第四节。

### 阶段 0：基线与策略

- **T01 固化基线**：记录 HEAD、工作树状态、正式实例只读状态、6 个对象的身份与保留期。
  交付：本文第一节的核对表。判据：复核结果与输入文档一致，差异被写明。依赖：无。
- **T02 定义清理策略（一次性确认的对象）**：新增策略结构：管理目录集合、允许直接删除的类别集合、观察天数（14/30）、每轮文件数与字节额度、通知出口、结果页目录。
  交付：`internal/cleanup/policy.go`；持久化在既有 `meta` 表（键 `cleanup.policy.v1`），JSON 校验严格；带自身 digest。
  判据：缺字段、越界、未知类别一律拒绝；默认值=14 天、无直删类别、macOS 通知。依赖：T01。
- **T03 类别判定**：把"这是什么类别"变成可检查的确定性函数（安装包/归档/文档/凭据/项目源码/临时名/未知）。
  交付：`internal/assess` 导出按名称分类的纯函数 + `cleanup.CategoryOf(rel)`。
  判据：同一路径在任何主机上得到同一类别；凭据类与项目源码类永不可直删。依赖：T02。
- **T04 三结果判定纯函数**：把"模型结论 + 本地安全事实 + 授权"映射为 delete/quarantine/keep 及其原因码。
  交付：`internal/cleanup/disposition.go`。
  判据：R04/R05/R14 的每一条都有独立用例；服务失败与"明确保留"产生不同原因码。依赖：T03。

### 阶段 1：双审核改造

- **T05 事实自动取得**：用程序测量的类别相关事实替换逐文件人工证明与完整副本；事实带来源标注，缺失就写缺失。
  交付：`internal/review` 重写（删除 `evidence.go` 的备份校验路径，新增事实构造）。
  判据：没有人工证据文件也能完成一次审核；无备份时不再一律拒绝；事实缺失时模型被明确要求回答 insufficient。依赖：T04。
- **T06 三结果输出**：审核返回结构化结论（disposition + 原因码 + 模型意见），不再只返回布尔许可。
  交付：`review.Outcome`；`Approval` 携带 disposition。
  判据：delete 只在双方明确同意永久删除时出现；任一方 keep 时 disposition 必为 keep。依赖：T05。
- **T07 提问语义分离**：永久删除与可逆隔离使用不同问题文本与判定准则，不得互相顶替。
  交付：`describeAction` 增加 `delete`（不可撤销），`quarantine`（可逆）。
  判据：delete 的问题文本明确"不得以可逆隔离或之后可恢复为由"。依赖：T05。
- **T08 反编造约束**：提示词与本地校验同时禁止用文件名、扩展名、时间单独推断"无用"；缺事实必须 insufficient。
  交付：提示词 + 用例（模型返回"因为文件名看起来是安装包所以可删"必须被本地拒绝或降级）。
  判据：事实缺失用例下不产生 delete。依赖：T06。

### 阶段 2：执行路径

- **T09 直删协议**：在既有执行器内新增"原路径永久删除"协议：身份/令牌/内容复查 → intent（action=delete，含审核快照）→ unlink → 目录 fsync + anchor barrier → 完成记账。
  交付：`internal/execute/delete.go`。
  判据：不经过 vault；不留裸 `os.Remove`；每一步失败都有可解释的中间态。依赖：T06。
- **T10 分流接入**：`Quarantine` 改为"先本地复查 + 稳定读，再审核，再按 disposition 分支"。
  交付：`internal/execute/quarantine.go` 重构。
  判据：keep 分支零移动零删除；delete 分支只在直删类别 + 有效 auto_purge 授权时可达。依赖：T09。
- **T11 保留的落账**：保留也必须留下可读记录（原因码 + 时间），且不阻塞范围继续处理。
  交付：item 状态收口 + `action=keep` 事件。
  判据：保留不产生 pending、不触发 held、不使范围停摆。依赖：T10。
- **T12 对账补分支**：`recovery` 认识 `delete` 的中间态（源在/源消失/源被换）。
  交付：`reconcileDelete`。
  判据：intent 已提交但未 unlink → 回退；已 unlink 未记账 → 以 RECONCILED_ABSENT 收口；源被替换 → hold。依赖：T09。
- **T13 观察期默认值与旧对象保护**：新对象保留期 = max(规则保留期, 策略观察天数)；旧对象保留期字段一字不改。
  交付：planner 绑定值来源调整。
  判据：策略 14 天不会把任何已有 30 天对象变短；带用例。依赖：T02。

### 阶段 3：到期复核与告知

- **T14 到期复核**：清空前依次检查：已恢复 / 被保护 / 新使用信号 / 文件变化 / 通知已送达。
  交付：`internal/run` 的到期队列前置检查 + `internal/execute` 复核。
  判据：任何一项不满足即跳过并给出原因，不消耗清空额度。依赖：T10。
- **T15 通知出口**：macOS 一次系统通知 + 固定结果页入口；送达结果落库（成功/失败都可查）。
  交付：`internal/notify`。
  判据：通知失败不会被记成"已通知"；无人值守环境（无 GUI 会话）也如实返回失败。依赖：T02。
- **T16 通知门禁**：进入隔离区时通知；永久清空前给简短提醒；提醒未送达则本轮不清空。
  交付：通知事件 + 清空前置条件。
  判据：伪造"日志写了"不能放行清空；带用例。依赖：T15。

### 阶段 4：结果页

- **T17 三区汇总**：从 `items + events` 汇总本轮真实结果，只认"完成且确认"的动作。
  交付：`internal/report/collect.go`。
  判据：planned/intent/模型意见/debug 模拟一律不计入"已删除"。依赖：T10。
- **T18 结果页渲染**：固定位置（默认 `<state>/reports/`）的 Markdown + JSON，三区字段完整。
  交付：`internal/report/render.go`。
  判据：R25 的字段逐项存在；超限显示总量与"还有 N 条"。依赖：T17。
- **T19 运行摘要**：`run` 结束时打印一行三区摘要，与结果页同源。
  交付：runner/CLI 输出。
  判据：数字与结果页一致，不允许两处各算一套。依赖：T18。

### 阶段 5：命令与文档

- **T20 `cleanup setup`**：一次性确认五件事，两步调用（先预览 digest，再确认），写入策略。
  交付：`cmd/dustkeeper/cmd_cleanup.go`。
  判据：不带 digest 不改任何状态；写入前展示将被批准的全部内容。依赖：T02。
- **T21 `cleanup report`**：打印/定位最近结果页；`--json` 输出机器可读。
  交付：同上。判据：只读，不触发任何文件动作。依赖：T18。
- **T22 文档**：README、`docs/operations.md` 增加三结果说明与"哪些还没验证"。
  判据：不出现"已实现零误删"之类断言；正式实例状态如实。依赖：T20。

### 阶段 6：验证

- **T23 单元与集成测试**：判定映射、策略、类别、结果页、通知失败、直删、对账。
  判据：`go build ./...` 与 `go test ./...` 全绿；新增用例覆盖 R04 四类保留原因。依赖：T18。
- **T24 隔离实例端到端**：独立 state/config 目录 + 临时目录，跑通四个分支（可删/可移动/保留/服务失败）。
  判据：每个分支的真实磁盘结果与记录一致；原始字节可核对。依赖：T23。
- **T25 真实模型分支**：在明确授权与调用上限下，对少量人工标注样本做真实双模型判断。
  判据：只记录真实返回；凭据不可用就如实写"未取得同意"，不得用假模型结果冒充。依赖：T24。
- **T26 安装一致性**：把通过验证的构建装成定时任务调用的版本；正式实例保持暂停，等待单独授权。
  判据：`version` 与 SHA-256、launchd 调用路径、暂停状态三者一致且被记录；不擅自 `resume`。依赖：T24。

### 反向验证（任务 → 需求）

逐条反查 T01–T26：每个任务都能指出它服务哪条 R；没有"为了做而做"的任务。三处看似冗余的设计是有意的：

1. **T04 与 T06 分开**：判定规则是纯函数，可在无网络、无文件的情况下穷举；审核返回结构是另一件事，混在一起就无法证明"服务失败不会被当成同意"。
2. **T14 与 T16 分开**：复核回答"这个对象还该不该删"，通知回答"用户是否可能知道"。合并会让"通知没送达"被静默成"复核通过"。
3. **T17 与 T18 分开**：取数与呈现分离，才能用同一份取数喂给 `run` 摘要、结果页和 `--json`，避免三处各算一套数字。

### 拆分过程中发现的、输入文档未明确规定的空白（以及处理方式）

| 空白 | 处理 |
|---|---|
| 直删与"待删除"共用同一次模型调用还是各调一次 | 只调一次：按"是否属于直删类别且授权有效"决定问哪个问题。省一半请求，且不会出现"隔离同意被当成删除同意" |
| 保留的对象下一轮是否重新送审 | 不重复送审：保留决定按路径 + 观察窗口记录，窗口内不再询问；窗口到期或文件变化后重新判断。理由：避免每天为同一批文件重复付费 |
| 通知"送达"如何判定 | 只认系统通知调用返回成功且非无人值守会话；结果写入事件。日志、终端输出都不算 |
| 结果页上限是多少 | 每区默认 200 条，超出显示总量与剩余条数（R30） |
| 直删是否也要"观察期" | 不需要：直删的前提就是类别可再生产 + 双方明确同意。观察期只服务"不确定能不能永久删"的对象 |
| 策略变更后旧计划是否失效 | 是。策略 digest 参与计划 digest，改类别/天数后旧计划必须重新生成 |
| 无人值守时通知必然失败怎么办 | 不清空（R27），但隔离照常（可恢复）；结果页仍然生成，`run` 明确报 `notify_failed` |
