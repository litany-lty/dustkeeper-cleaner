# Dustkeeper 下一阶段能力建设与缺陷修复方案

2026-11-15（北京时间）｜给产品负责人、DeepSeek 实施者和验收者｜分析基线为仓库 `85e99db`，本机安装版为 `88097e4`、数据库 schema 6。本文是实施依据，文中标为“拟议”的能力、命令或授权类型尚未交付。

**阅读顺序。** 负责人先读第一、二节和第九节的达标线。实施者从第三节 F1 和第九节 W1 开始，做缓存或安装包时再读第五、六节。现场定位以第十节的回执为准。

## 一、产品要交付什么

磁盘紧张时，用户想知道三个答案：“空间花在哪里？”“哪些东西可以清，清后会失去什么？”“你实际替我腾出了多少空间？” 对同一台机器，同样重要的第四个答案是：“上次说过要保留的东西，这次还认得吗？”

Dustkeeper 已有能够保护**某个已登记文件**的执行内核。缺口在前后两端。前端不会从整台机器的占用一路找到有处置依据的任务；后端不会完成大量实际有效的操作，例如调用包管理器回收缓存，或者把一组旧构建作为整体处理。中间还有一个会让符合条件的文件长期排不到的规划缺陷。单独放开删除权限、调大模型预算或把根目录注册成清理范围，都解决不了这三个问题。

**首个可交付版本**应达到以下效果：本机能分段盘点，在只读报告中说明可见范围与大头；定时任务能绕开已有保留决定，处理下一个合资格候选；至少一种经过用户类别授权的可重建缓存由 Dustkeeper 的正式入口自行处理；用户从一条运行记录能看到原因、动作和空间变化。只完成其中一段，就按该段交付。其余能力按本文后面的顺序增量开放。

## 三、先修已证实的问题

### F1　已保留的对象占掉唯一名额，后面的候选得不到机会（P0）

**复现链。** 观察记录按相对路径排序。规划器读取记录时先受 `MaxFiles` 限制，一份 1 文件计划很快满额。执行器之后才查询近期有效的 keep；同一个文件身份及版本未变时，当场返回保留，不再问模型。11 月 9 日该证书包因无法确认移动安全而保留。11 月 15 日它又获唯一名额，执行阶段复用了旧结论，同轮无递补。这解释了为什么入口修好以后仍无产出。[观察顺序](../../internal/store/observations.go) · [规划器](../../internal/plan/planner.go) · [执行阶段的复用](../../internal/execute/quarantine.go) · [保留记录匹配](../../internal/execute/keep.go)

**最小修法。** 在**自动计划的名额分配前**排除仍处于有效保留期的原对象版本，继续向后找。规划前批量取相关范围的保留摘要，供迭代器以只读数据查询。迭代器持有单一数据库连接，在回调中再逐项查库会造成阻塞。执行前仍做完整复核，规划阶段的结果没有写入权。先复用一份匹配逻辑，验证用原对象身份、变更令牌、规则/范围绑定和有效期限，不能只用路径。旧证据不完整时回到现有核验流程。人工点选、只读规则预览和已冻结计划的摘要语义保持兼容，自动计划额外标明跳过原因。

**不能把失败当保留。** 真正的保留决定、预算用完而未发出请求、请求已发但结果或费用未知，分别进入保留期、可再排队、等待对账三条路。未知请求不得因“调到队尾”在下一轮重复付费。只有本轮没有合资格对象，才写“无可处理候选”。如果规则仍匹配 20 个，应同时写明多少在保留期、多少超额、多少未评估、最早何时可能再处理。

**验收。** 在临时范围放 A 和 B，A 已有有效 keep，B 合规，每轮上限 1。B 在同一轮获得名额，A 的新增 HTTP 为 0。改变 A 的内容或令牌后旧 keep 不再挡住重新评估；把 A 换成“已发未结算”时仍保持冻结。所有对象都在保留期时得到可解释的零动作回执。不要用增加上限让用例通过。

### F2　启动器和定时器使用不同的实例校验，失败后长时间没有有效工作（P0）

Mac 第三轮在启动核心程序前因启动参数不匹配被拒绝，审核派发为 0。外层账本停住，后续日程一直遭拒。11 月 15 日已修正本机私有入口对实际启动参数的校验和逐失败轮恢复方式，第四轮手动成功。**现场补丁已经做过，待修的是将修法纳入可发布安装、升级和验收流程。** 不重新初始化账本，也不重放历史失败。

安装时用同一份描述生成并验证调度命令、实际核心路径、配置、状态库和预算账本。校验受管包装器及其绑定的核心，区分“从未派发”和“已派发结果未知”；只允许恢复明确核实过的失败轮。诊断输出应同时给出“定时器已加载、最后自然触发、最后有效扫描、连续被拒次数、下次干什么”。Mac 用 launchd、Linux 用 systemd，复用判断契约即可，各平台保留正常安装方式。自然触发的证据至少能关联日历触发时刻、调度进程、唯一 run ID 和本轮回执。手动启动只验证入口。参见 [调度模板](../../internal/schedule/render.go) 和 [已部署的服务器服务单元](../../deploy/elidli/dustkeeper-elidli.service)。

### F3　空结果缺乏解释，容易被当成验收通过（P0）

用户应能分清“没有垃圾”“有候选，全部受保护”“有可做的，但权限不足”“本轮被预算截断”“程序根本没启动”。扫描数、规则匹配数、合资格数、入计划数、送审数、物理动作完成数应各有来源。一次遍历提前截断时，只把实际计算过的部分列作精确计数；其余显示未评估。重复命中同一个保留决定可记一条本轮摘要，并附旧决定的 ID 与时间，不新造一次模型判断，也不重复记入历史处置总量。对无候选的正常运行也应生成可读报告。[结果汇总](../../internal/report/collect.go) · [现有可读日志包装器](../../scripts/run-readable-log.py)

## 四、扩大“看见”的范围，同时约束“能动”的范围

给用户两个明确动作。“盘点本机”只读已可访问的文件系统元数据，回答空间归属。“处理这一类”只对已授权主机、目录、对象类型和动作生效。盘点根目录不会创建清理作用域，也不会向外部模型发送全盘路径。开发时把这条隔离做成可验证的接口约束，不能靠命令帮助文字维持。

**第一版盘点。** 默认从用户选择的本地数据卷开始，限定设备号、不跟随符号链接、不触发云占位文件内容下载。按目录聚合分配量，输出前 N 个不重叠大类和大文件，父子表标明“已包含”。为硬链接按设备与 inode 去重，稀疏文件并列显示逻辑与分配大小。APFS 克隆、快照和仍打开的已删除文件可能使块数之和与整卷差值不同，未测量的共享块写未知。Linux 容器层、挂载和不同卷也分别计算。第一版无需构建全机内容哈希或识别所有重复文件。

**完整性与性能。** 在现有受管扫描器已有的 epoch、目录队列、故障目录和预算思想上实现只读卷盘点；独立保存有界汇总和游标，不能把全卷九百万条路径注入当前要执行清理的观察表。先给目录排行，再对用户关心的大头补充用途和引用。达到 I/O、时间或条目预算时落下进度并返回部分结果，下一次从未完成的目录继续。记录“已覆盖、权限不可读、按策略跳过、尚未访问”及本轮/累计范围。目录改变、卷重挂或中断时，只撤销受影响的增量结论；macOS 事件流或 Linux 通知可在后期用来加速，不能作为唯一事实来源。[受管扫描实现](../../internal/scan/scanner.go) · [独立只读评估入口](../../cmd/cleanup-report/main.go) · [现有文件评估器](../../internal/assess/scan.go)

**如何衡量。** 保存扫描时间、条目/字节、峰值内存、账本/索引增长、冷扫和续扫耗时。内存与持久化开销应能给出上限。按同一设备、相近时间窗对代表目录抽样与系统统计对照，解释差额。拒绝访问按原因计数，用户确有需要时再说明提供访问的收益。对于磁盘已十分紧张的场景，优先复用最近的完整快照并验证少数高价值对象，避免为“找垃圾”反而写出巨大的索引或报告。

## 五、让“这是什么、谁依赖它、如何恢复”成为可执行的能力

### 5.1 从单个文件扩展到有边界的一组对象

采用小步设计。先在仓库内写一种固定的工具适配器，跑通“发现 → 计划 → 核验 → 执行 → 回读”，第二种实现出现时再抽共同接口。文件隔离继续走现有执行器；清缓存、清生成目录或截断日志有各自的成功条件和恢复方法。首版不加载第三方插件，也不接受用户配置中的任意 shell。

| 拟议记录 | 必须回答的问题 | 失效和失败时怎么办 |
|---|---|---|
| 候选 | 属于哪个主机、卷、类别、生产工具；对象是单文件、文件树、还是由工具管理的缓存；有无逻辑/分配量和观测时间 | 多个来源发现同一对象要去重。父目录和子文件只能择一计收益。 |
| 用途与引用 | 这是原件、已安装运行时、唯一恢复介质、生成品还是缓存？哪些检查是命中、排除、不可见或不适用？ | 活跃引用直接保留。与该类动作相关的关键证据未知，只读报告列原因或请用户选；无关探测缺失不应拖住所有对象。 |
| 动作计划 | 具体工具/版本、参数、预期影响范围、所需权限、可回收区间、恢复步骤、最迟执行时间、绑定授权和证据摘要 | 计划编制后安装入口、工作树、缓存路径或成员身份改变，旧计划失效。以用户可读的对象名给出差异。 |
| 执行与回执 | 操作 ID、动作开始前意图、已完成成员、工具退出原因、实际验证、字节来源、还有什么没做 | 不可逆操作先落意图。中断后回读剩余成员或工具状态，能确证的结算，无法判明则挂起；重新启动不再盲跑整批。 |

**批量语义是关键。** “每轮 1 文件/1 GiB”的原授权不适用于“一个目录即一次动作”。一个缓存动作可能处理几十万个条目。新授权须描述主机、工具管理的精确根、允许动的类别、单次字节或其他可验证影响上限、频率以及何时可无人值守。如果官方工具只支持全量清缓存，无法限制在本轮预算内，就只能预览、请求覆盖整个动作的一次授权，或选用有界原语；不能分批偷渡，也不能拿缓存命令的退出 0 代替事后核实。二进制和参数从本地可信安装路径解析，用参数数组调用，执行前再读工具自己的缓存根。外部配置、文件名、压缩包内容、模型输出都不能拼成命令。

| **下载的安装介质，P1** | 识别产品、版本、平台、架构和安装位置。对 macOS 核对 bundle 标识/版本、已挂载镜像、活动安装任务；需要可重取时核实相同版本和架构的可信发行来源，记录链接/清单和验证日期。来源失效会让旧计划失效。 | 程序名相似、存在更新版本、装有下载器都不能证明旧版本可重取。离线授权软件、签名不明、混合 ZIP、恢复包默认留置。对 Unity 应先核实精确发行来源，再移除安装包；保留编辑器。确认式清理只处理回执列出的成员。 |
| **IDE 和浏览器缓存，P2** | 独立识别可重建索引、旧更新补丁、下载归档等叶子位置；应用是否运行、该版本是否还在使用是执行条件。按工具版本维护小范围规则，版本未知只盘点。 | 同一个 JetBrains 缓存根里还装有 ACP 代理运行时、Local History、插件、浏览器 Cookies 和 Local Storage。禁止仅凭父目录名处理。夹具中保留这些哨兵文件，索引下一次可初始化。 |
| **项目发布/验证副本，P2** | 利用现有 `internal/retention` 的完整发布集合思想，由适配器提供当前安装入口、版本清单、组件身份、原版备份、验收引用、回退点及进行中的安装。先生成“保留哪套，为什么”的报告。[发布集合规划](../../internal/retention/plan.go) | 该包今天接收声明清单，只出保留计划，不自行发现真实引用或执行。按应用合并保护，任一活跃引用胜出。目录名可能与包内 build ID 不同。验收用指向旧目录的当前应用符号链接，最终验证它仍解析至同一可执行文件。 |
| **应用与系统日志，P2** | 识别生产者、当前文件描述符、是否为已轮转日志、服务支持的轮转/重开方式。区分“删除已关闭历史轮转”“原位清一次历史内容”“修改长期日志策略”。应用日志保留天数、审计义务和是否可损失须来自用户或现有策略。 | 活跃写入日志不能简单 unlink，否则路径消失但进程仍占块。慢查询日志是诊断资料，不作为缓存长期默认清空。截断、轮转、改配置、停止服务分别授权；按动作核 inode、权限、进程和是否实际观察到后续写入。另报短期重复增长，便于修上游原因。 |
| **课程、视频及用户原件，保护优先** | 先做只读的应用引用解析。快学可查当前/历史课程库中的源路径、已处理条目和可用身份，再查转录、笔记、sidecar 与项目证据。文件名、大小、Spotlight、访问/修改时间均只能辅助。记录用户的保留意图并在未来候选上重新匹配。 | 快学原片保护与编译产物清理可并存。对旧路径移动或改名，尽可能按稳定身份/现有指纹匹配，无法确定时留置。62 个 B 站目录有项目索引引用，全组保留。其他来源无记录不证明可删；删除用户原件仍需精确清单及当次明确决定。 |
| **Docker、虚拟机、数据库、应用数据，先只读** | 报分配量，展示拥有者、依赖与官方维护入口；后续有需求时再做专门适配器。如 Docker 的镜像、构建缓存和持久卷必须分开说明。 | 不从宿主机删除 Docker.raw、虚拟盘、.ibd、SQLite 历史、聊天数据来回收空间。删一个数据库文件和让数据库产品执行受支持的维护是完全不同的操作；这一类不阻塞首版交付。 |

**第一个适配器如何落地。** 以 uv 为例，先在临时工具环境里让同一版本的 uv 确认缓存根和 prune 语义，验证它是否支持预览；缺少预览就只展示“整个缓存最多占多少、可回收下限未知”。执行层用已登记的可信程序和固定参数调用，覆盖环境中可能重定向缓存位置的设置，只允许命中本次计划的根。若调用期间新装依赖、工具无法取得自身锁或版本改变，应退回重新评估。完成后保留工具报告的数值和目录实测数值，检查已安装命令仍能解析至原工具环境。若崩溃发生在调用后、记账前，先核对缓存和执行回执，再决定是否能标为部分完成。这个例子证明“工具清理”能形成一项独立动作，不能作为任意目录删除的通用接口。

### 5.3 调度应服务于用户的磁盘目标

第一版先按已批准的类别和确定性证据排队。把当前在用和不合资格的对象排除后，优先可重建、预计收益明显、检查开销低的对象。在同等级内按等待时间轮转；达不到单项上限的大对象列作“超限待选择”，不阻挡后面的合规小对象。筛选只负责选哪些值得进一步核验，正式安全判断仍在执行时做。

再考虑“空间低于用户设置的水位才清、达到目标即停”。磁盘充裕时可只更新盘点。给用户同时展示潜在收益、重建时间/下载量、需重启的软件与最早可回收日期。只要仍有可做任务，就不能总让字典序最前的文件或第一个范围占满全部机会。某些阶段状态不清时只停受影响对象；涉及账本可信度、共用费用上限或全局暂停标记时则停整个实例。**健康的零动作是一种成果，必须可以解释；磁盘洁净度不能用每天删多少来奖励。**

## 六、权限、恢复和审核如何衔接

1. **区分四件事。** 发现对象、建议处理、获准执行一次、获准以后定期执行，分别留痕。作用域已登记也不等于可永久清空。规则变更提供新增/移除类别、影响对象和边界差异；用户能撤销单类或暂停实例。权限不足要输出具体的拟处理对象、预计收益和授权后果，避免让用户对整台机器给空白同意。
2. **明确主机边界。** 本机 Downloads 的旧规则只有隔离授权，elidli 的“至少 7 天后、复查通过才可清空”只覆盖它的受管范围。今天对 Mac 缓存、日志、安装包或 19 个视频的一次性批准，不能变成长期规则。现有模型请求总次数限制虽已解除，批次约束、对外发送数据范围、每端 35 元且合计 70 元的费用边界仍单独约束。新类别元数据涉及更多个人或商业信息，默认留在本地。
3. **把恢复方式说清。** 隔离对象可用原恢复流程，记录最早到期日、目标冲突处理和真实回读。包缓存/编译产物只有重下或重建，不能承诺精确还原此前字节。原始资料、旧专有软件、发布回退包若只有一份，“可以还原”的依据须能落到独立副本或已验证流程。进入隔离只做同卷移动，文件内容尚占空间。到期清空仍按隔离时绑定的授权、保留期及当下检查执行。新授权不追溯解锁旧对象。
4. **让模型处理真正的语义歧义。** 先本地发现、去重、查引用和权限，有确定保护理由直接留置；同一有效保留结论不重复付费。按已确认的 JEV / MiniMax 模式审当前受管文件，保留拒绝、超时、意见分歧和依据不足各自的语义。模型不能证明“可重装”、创造授权或否定已知活跃引用。未来若希望纯本地、官方工具回收可再生缓存，须明确建成一种独立动作与批准模式，列清工具将永久回收什么，由用户选择策略；在批准之前只预览，绝不能在现有文件隔离/删除路径加隐藏的“跳过双审”开关。
5. **行动可追溯。** 使用私有权限保存最少的运行证据，期限与体积有上限。外发只限获批字段和端点，默认不传文件正文、整机路径清单、课程标题集合、数据库行、账户、密钥或工具输出全文。遇到平台明确拒绝某动作时，记录拒绝层和原因，遵守有效边界；若提示允许更窄操作，应先核实差异，不能把换一个命令名当作获得权限。绝不让模型输出 shell 字符串作为执行计划。

## 七、让无人值守执行既能继续，也能停在正确的位置

| 运行状态 | 下次如何处理 | 回执至少应写什么 |
|---|---|---|
| 合规零动作或保留期内跳过 | 继续其他合规候选；全部已处理则正常结束 | 上次决定、失效条件、候选分布，下次可能有变化的时间 |
| 按预算主动止步且明确没有派发 | 保存进度，下轮从未做的对象开始 | 截断原因、剩余工作、HTTP 为 0 的证据 |
| 模型确已响应、处置为保留 | 按精确对象版本复用结论 | 关联 review ID、两阶段结果、无需保存模型自由文本 |
| 提交后超时、未知费用或回执缺失 | 保留原派发/预留，通过正常对账流程处理；禁止自动重发 | 对应请求/轮次、能查到的用量、缺的证据、影响范围和恢复办法 |
| 进程中断、动作可能只完成一半 | 按持久意图与工具状态对账；无法证明的成员不重复执行 | 已完成、未开始、未知分别记数；原对象、当前身份与恢复入口 |
| 离线、工具版本不支持、文件或路径变动 | 跳过受影响类型，生成可解释故障；权限或身份不符不回退到另一个实例 | 具体能力不具备的原因，何时可以再测；可操作的修复建议 |

今天的 HTTP 计数、token/套餐用量、预算占用、供应商实际新增费用是四笔不同的账。服务器包装器每轮预留 0.01 元，只有新回执证明零 HTTP 才退回。应显示“预留 / 已核实用量 / 已核实新增费用 / 未知”，按真实 run 与 dispatch 关联。固定预留**没有天然等同于实际费用上界**；若要严格承诺硬上限，应有可验证的输入/输出上限、有效费率或套餐证明、账户侧限制和预留对账。任一不可证明且会影响已批准预算时，继续暂停付费动作。MiniMax 是订阅凭据，记录订阅额度，不换算成按次现金。历史未知项不能填零，也不以重新请求来核费。[服务器受控入口](../../scripts/run-scheduled-log.py) · [派发与对账](../../internal/store/review_dispatch.go)

打包时要解决 Mac 私有脚本、仓库模板、Linux 实际服务参数之间的漂移。用一份可读、受限权限的安装描述记录核心版本/制品摘要、实例和账本路径、包装器、服务账号、时区、触发方式、超时和宿主特例。安装后从操作系统回读实际配置做比对。elidli 当前特例不必照搬到所有 Linux 主机；新平台先只读探测。恢复、预算告警和“连续多天未成功扫描”尽量走现有调度与日志，不新增第二个常驻代理。

**回执本身也要验真（代码可见的风险，未发现现场事故）。** 服务器包装器的 `_receipt` 会先把 run ID 转为字符串，JSON 中的 `null` 可变成非空文本；时间检查验证了起点下界和起止顺序，却没有比较结束时间与本地收件时间的上界。部分完成分支对缺失的 scope 列表使用空数组，遍历空数组不能证明“只有预算中断”。这些条件各自都不足以把一份回执绑定到本次调用。W2 可用一个真实成功回执做最小变体：将 ID 填 null、把完整时间窗移到未来、或在部分完成时移除必需的范围信息。分别应拒绝结算且保留预留。实现应与本次核心运行 ID 映射、预期范围、进程退出和有界时钟容差交叉验证，同时保留有效的零请求回执与合法的预算中断。不要把这些静态风险写成已经错扣或退款。

## 八、结果怎么量，产品才能越用越好

可读报告第一页只需要回答“本轮为什么运行、覆盖了哪里、做了多少、有哪些没做、接下来怎么办”。结构化明细保留相同数字和 run ID，供定位具体对象。以下是拟议的报告字段语义，应复用现有报告版本与关联方式，旧回执缺字段就显示未知。

| 指标 | 口径与用途 |
|---|---|
| 候选分布 | 依次记录发现、合资格、因已有决定跳过、引用保护、待授权、超额、选入、未评估。每个阶段给出分母，避免将未处理的尾部当作已检查。 |
| 动作结果 | 沿用已删除、待删除（已隔离）、保留。再单列工具回收、截断、失败、部分完成和待对账，区分按文件计数与按缓存动作计数。成功以执行后同一身份的回读和完成记录为依据。 |
| 空间 | 逻辑字节、已分配块、工具估算/回报、隔离区净变化及指定卷前后可用字节分别带来源。并发动作共享一次整卷测量，不把同一份增量按任务重复求和。无法单独归因时显示“同期净增”，零和未知分别显示。 |
| 时间与成本 | 扫描、取证、模型等待、执行、验证各耗时；派发与未派发分开，保留真实 HTTP 次数、供应商用量状态和账本占用。发现千万文件不应对应千万次模型调用。 |
| 产品质量 | 在人工已确认、有标签的样本上分开统计误删/误移、漏掉的可清量、错误保留和明确弃判。按类别与字节数报告样本量。恢复请求是误判线索，用户没要求恢复不能证明分类正确。用“在有合格候选的轮次中，多少轮无需人工代办且有回执”衡量自动性。 |

**例：本轮零动作时应该看到什么。** 按 11 月 15 日这次事实，可写“Downloads 扫描 1,408 文件；唯一计划项命中历史保留；今日新增模型请求 0；已隔离/已删除均 0”。当前程序没有计算的“还有多少可递补项”须标未知。改进后补上真实递补结果和下一轮条件。历史 48.10 GiB 的外部清理记录可作为比较样本，但不回填成 Dustkeeper 成绩。

**反馈怎样生效。** 用户选择“这是原片”“它是当前运行版本”“这类官方缓存允许定期回收”时，分别保存对象保护、引用关系或类别授权，附适用范围和来源。文件改名、版本升级、目录迁移或用户撤销时重新判断。不要把一次接受删除训练成所有相似后缀的通用偏好。优先从多轮重复跳过、高成本低收益、连续暂停等信号发现规则缺陷，先做离线有标签回放，再决定是否需要付费评估模型。原始文件正文不进入反馈库。

## 九、交给实施者的工作顺序

每个工作包只补一个实际缺口。下面的命令/结构若标为“拟议”，需要实现后才存在。依赖顺序优先于并行数量。

| 工作包 | 主要落点和交付 | 完成判据 |
|---|---|---|
| **W1　修正候选阻塞** | 修改 [planner.go](../../internal/plan/planner.go)、[keep.go](../../internal/execute/keep.go) 及必要的 [store](../../internal/store/intents.go) 查询。在自动规划前过滤有效 keep 和确证应暂缓的项，保留执行前重验，增加零动作原因。 | F1 的 A/B 用例先复现旧失败，再通过；上限 1 不变，B 获得名额、A 无新增审核。手动计划和旧回执兼容。 |
| **W2　可安装、可诊断的调度入口** | 将 11 月 15 日本机已修的参数/恢复语义移入受版本控制的安装流程；将 `doctor`、调度模板、运行入口和费用账本的实例信息连起来。明确 Linux 服务账号/硬超时与通用模板的差异，有依据才统一。 | 一个正常夹具和一个错绑实例夹具；错绑在派发前拒绝且不写其他实例。重复恢复同轮不生效。之后在有对应许可的机器上，查一轮真实自然触发及回执。 |
| **W3　可续扫的本机空间报告** | 先做受限元数据遍历、卷身份、目录汇总、Top N、读取错误、游标与覆盖率，再接拟议的 `inventory` 用户入口。与现有 `cleanup-report` 共用计量/分类，不复制行动权限。 | 通过可控的小条目限额强制中断一次，续扫抵达尾部大文件，父子、硬链、稀疏文件计量正确；受限子树可见，删除、模型调用和管理授权新增均为 0。 |
| **W4　首个工具回收动作** | 从 5.2 表中选**一种**行为明确定义的缓存工具。交付只读预览、类别授权描述、固定参数执行、结果回读、异常对账、报告。优先让“同一入口能做事”跑通，再抽适配器接口。 | 专用缓存目录中有可再生内容和受保护环境。预览不改变大小，获准时操作确有收益，保留环境仍可用；中断后未知项不盲重试，第二次正常运行变为可解释零动作。 |
| **W5　逐类扩展** | 次序建议为编译结果 → 安装介质 → 发布验证副本 → 日志。并行建设快学/项目引用解析，让课程和运行数据能得到持久保护。Docker、数据库、虚拟机维持只读盘点，直至有真实业务需求和专门适配器。 | 每个类别至少一个“应处理”和一个“看起来像垃圾但必须留下”的代表样本。真实宿主缺少资格的对象就记为未覆盖，不用伪造垃圾补数。 |

**W1 另有一个规模风险。** 当前执行期在重试窗口只读取最近 500 条 keep。若某个早先的有效决定被 500 条其他对象的事件挤出，可能造成额外付费重问；未在现场证明已发生。不要将这段逻辑原样搬进规划器。优先尝试按对象键做定向查询，或对相关 scope 分页并批量构建索引，必要时才加数据库索引/投影。用超过 500 条无关事件的夹具复现。过滤未决请求要沿用该请求的精确对象、动作和绑定；人工解除 A 的未决记录不会解除 B，更不会让其他已冻结范围继续付费。[现有查询](../../internal/store/intents.go) · [执行期判断](../../internal/execute/keep.go) · [精确解除测试](../../internal/execute/dispatch_test.go)

**兼容和回退。** W1 优先保持原 schema。确需持久化扫描进度、新授权或工具意图时，使用显式、版本化迁移，增加可忽略字段或独立表，写清老二进制可否读取。已有审计、未决派发、旧隔离保留期与按主机分配的 35 元账本不重置。回退优先暂停新类别并恢复上一个兼容程序；数据库若有新的真实动作，不能用升级前快照直接覆盖，否则会丢失“已经删过什么”。升级前后核实作用域、授权、未决项和恢复入口。针对某一工具的新故障可以单独禁用该工具，而不影响正常的只读盘点。

### 验收分四层，缺哪层就写哪层

1. **实现层。** 临时目录、离线夹具和有针对性的 Go/Python 测试，验证输入输出及关键失败分支。已有用例可复用，如 `TestHeldUnknownRequestLiftsOnlyResolvedDispatch`、`TestOnlyFinishedActionsCount`、`TestUnknownRequestFactsAreNotZeroFilled`。新增 F1 和 W4 的缺口用例。命令示例：在仓库根执行 `go test ./internal/execute -run '^TestHeldUnknownRequestLiftsOnlyResolvedDispatch$' -v`；查看实际运行的测试名，空匹配不算通过。选择与本次改动有关的包即可。
2. **安装层。** 记录目标主机、安装制品 SHA、版本、数据库 schema、实例根、调度实际参数和最近回执。通过已安装的正式入口跑一次，不用开发机临时脚本替它执行。手动实跑与自然触发分开标记；本次提案本身不触发新部署。
3. **业务层。** 选择一个既有资格又获得相符授权的真实对象，记录同一卷前后可用量、对象前后状态、真正的执行主体与受保护对照。缓存须验证重建能力或上游官方回收结果；隔离须能按 ID 恢复；永久清空须自然达到已批准的保留期限。运行成功但没有对象，只能验证空载路径。
4. **无人值守层。** 在用户认可的已有日程内，至少观察一次自然触发完成真实的已授权动作，以及一次跨轮结果（已处理不再重复，保留期内不重问，或暂停后不重复扣费）。若自然窗口没有符合条件的对象，分别报告“调度通过”和“实际收益待观察”，不加密日程、不挪时间戳。历史计划里另有连续四次自然触发的观察约定，应复用真实回执、单独核对，不能用一次冒充四次。

**正式达标线。** 对某主机某类别可以作出这样一句有证据的承诺：“用户一次批准这个类别后，某天的自然日程找到一个真实且合规的对象，由已安装的 Dustkeeper 自行完成处理，保留应保留的对象，并自动生成能追溯动作和空间的报告。” 缺一段就在发布说明中写明缺口。对敏感原件，正确识别保护并停止可以通过保护验收，不能记作空间回收验收。
