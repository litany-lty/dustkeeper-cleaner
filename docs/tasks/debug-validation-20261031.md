# Debug 模拟清理实现与验收

日期：2026-10-31，Asia/Shanghai。

## 交付状态

已新增 `dustkeeper debug`：真实扫描与文件证据、JEV和MiniMax独立判断、文件复验；只生成模拟结果。默认零模型调用，`--execute` 才发请求。实际删除量固定0，不打开或修改正式状态库，不产生正式删除/隔离记录。

默认每轮3个候选、最多6次请求，最多盘点500项，120秒总期限，64 MiB总读取预算。可通过参数选择更小范围。任何接口异常停止本轮；证据不足、任何模型拒绝、文件变化都保留。两模型同意也只记录模拟结果，仍标记待人工复核，不产生正式权限。

操作说明见 [debug-mode.md](../debug-mode.md)。源码目录：`/Users/litany/WorkBuddy/清理器`。

## 实测与修复

1. Debug默认入口不读密钥、不创建数据库、不调用模型；真实审核组件经本机假服务可模拟放行，原文件内容及原数据库字节不变。
2. 已知引用优先保留；审核期间源文件变化会被拒绝。模型请求计数包含失败请求且有上限。
3. 原流程在JEV拒绝后不调用MiniMax，不利于debug定位分歧。现在debug会获取独立第二意见；第二意见不能覆盖JEV拒绝。正常执行继续使用原有短路规则。
4. 实际MiniMax消息多带 `base_resp`，严格解析误拒绝成功响应。已兼容可选状态对象，状态必须为0。状态缺失、非零、结构异常继续拒绝。[MiniMax官方客户端状态处理](https://github.com/MiniMax-AI/MiniMax-MCP/blob/main/minimax_mcp/client.py)
5. 实际用量多带 `output_tokens_details`。已兼容非负整数明细；核心用量的缺失、空值、负数和错误类型继续拒绝。没有把用量异常记成0。
6. 报告新增安全的接口结构错误原因；不会输出密钥、原始响应或thinking正文。新增简短判定理由和缺失证据类别，并拒绝带未解决缺口的矛盾放行。

## 真实模型结果

所有材料均为本轮创建的非业务测试文件，不包含Downloads或其它真实业务文档。测试访问/修改时间人为设定；不能据此推断真实文件已长时间未用。读取可能被系统记为近期访问，首次零调用的保留结果亦留存。

最终完整双模型轮次：4次请求，退出码0；收到 `jev-1.14.0` 和 `MiniMax-M3.1-Flash` 的有效响应，2个候选均未获放行。

| 测试材料 | 结果 | 说明 |
|---|---|---|
| 单次任务已结束的临时导出 | 两模型均信息不足，保留 | 正例未放行，召回能力未验收；用途仍是声明，完整引用覆盖及内容语义没有得到证明 |
| 用途不明的旧笔记 | 两模型均信息不足，保留 | 符合“不确定就保留” |
| 已知仍被引用的账单 | 本地保留，不发模型 | 引用事实优先 |
| 近期报告 | 本地保留，不发模型 | 近期活动优先 |

累计18次真实请求尝试，包含供应商诊断与超时；用户已明确此次不限制调用费用，程序仍按单轮上限执行。没有核对供应商账单，不估报人民币费用。阈值未降低。

简短判定说明功能的最后一次真实复验遇MiniMax网络错误，已停止并保留失败记录；该新说明字段只通过本地假服务验证。不能把此前成功的双模型响应当作该字段的真实验收。
