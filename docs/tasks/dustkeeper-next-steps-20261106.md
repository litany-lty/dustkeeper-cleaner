## 1. 结论：接下来按六步收口

当前代码已经完成本轮缺陷修复和运行数据接口。下一步依次完成：

1. 获得明确的远程发布许可，推送修复分支并创建 PR。
2. 跑完 Linux/macOS 原生 CI，合并并固定最终制品。
3. 在一个明确范围的目标实例上备份、显式升级、核对状态。
4. 用最终制品完成一次获准的小范围真实运行。
5. 验证真实调度触发，再观察后续 3 次预定触发。
6. 导出运行数据，完成一份验收记录，转入维护。

本轮不安排新功能开发。后续代码修改只针对上述步骤中实际出现、能够复现且影响结果的缺陷。没有具体问题，就按完成标准结束。

“可用”分三层记录：**源码可发布、目标实例可运行、有限范围可自动运行**。不要用本地编译通过代替后两层，也不要因尚无长期数据而重新开启架构改造。

## 4. 第二步：原生 CI 通过，固定最终制品

### 4.1 必须通过的现有门禁

两个目标为 `linux-amd64` 与 `darwin-arm64`，沿用现有 workflow：

| 门禁 | 通过条件 |

| build / vet | 成功 |
| 全量 Go 测试 | 本轮候选执行成功，重点包含升级、请求持久化、Q/P、结果汇总与恢复相关用例 |
| Python 回归 | 当前脚本测试全部成功 |
| race | 全量执行成功 |
| 发布与冒烟 | 目标制品构建成功，现有文件动作冒烟通过 |
| 制品核验与归档 | manifest、SHA-256、实际 version 对应，四件文件成功归档 |

`test/eval` 没有真实端点而 skip，必须单列为未运行的模型评测；不能把 skip 解释为模型准确率验证。这里不增加批量付费评测。

CI 失败时，只修复能够定位的失败及其必要回归。不要为了变绿去放宽文件系统要求、关闭失败用例或更改产品阈值。

### 4.2 合并与制品选择

1. 两个平台通过后合并 PR。
2. 记录最终 main 的完整 SHA。
3. 等待该 main 提交的发布工作流完成。
4. 从这次运行取得正式候选制品。

**PR head、PR 临时合并 SHA、最终 main SHA 可能不同。** 发布记录必须说明实际构建的 commit，不把它们混写。部署使用最终 main 对应的制品，不临时在服务器重编译一份来替代。

每个平台保存同一次构建的四个文件：

- 二进制；
- `SHA256SUMS`；
- `release-manifest.txt`；
- `build-facts.txt`。

另外携带同一提交的 `scripts/collect-run-data.py`；需要可读包装报告时，再携带 `scripts/run-readable-log.py`。脚本的来源 commit 也写入记录，不另建打包系统。

### 完成标准

最终 main 的双平台 CI 成功，下载的二进制 SHA-256、manifest commit/target 和实际 `version` 对应。到这里可称“本轮源码与发布制品通过门禁”，尚不能称“生产已运行”。

## 5. 第三步：选择一个目标实例，完成显式升级

### 5.1 先填写实际部署对象

优先沿用已批准的正式账号、目录、额度、模型端点与通知选择。下表必须用目标机事实填写，不能从旧验收记录猜：

| 字段 | 本次实际值 |
|---|---|
| 主机 / 系统 / 架构 / 文件系统 | 待填写 |
| 运行账号 | 待填写 |
| 最终二进制绝对路径 | 待填写 |
| 配置目录 / 状态目录 | 待填写 |
| 所有登记 scope 及本次获准范围 | 待填写 |
| 现有 timer/service 或 plist 名称 | 待填写 |
| 旧二进制 commit / schema | 待填写 |
| 新二进制 commit / SHA-256 | 待填写 |
| 实际 JEV 阈值 / 代理 / 两层模型 | 待填写；凭据值不进记录 |
| 通知选择 | 沿用已确认的 `none`，除非本次明确变更 |
| 备份位置与停机时间 | 待填写 |

**当前 `run` 没有 `--scope` 参数。** 它会按实例处理对账与后续工作。单目录首跑优先选择只管理该目录的实例；若既有实例管理多个 scope，必须把整轮可能触达的对账、到期队列和授权范围一并核对。不能把“只预览了一条规则”当成“整轮只可能操作这一个目录”。不要为此临时新增过滤命令。

### 5.2 停调度并保存一致状态

1. 停止实际使用的调度单元，确认不会再次触发。
2. 请求程序暂停，等待在途进程退出到安全边界。
3. 确认没有进程持有该实例锁，再保存同一停机点的完整数据。

需要一起保存的四类内容：

| 内容 | 范围 |
|---|---|
| 配置 | 完整配置目录 |
| 状态库 | `state.db`，以及存在的 `-journal`、`-wal`、`-shm` |
| 隔离与身份资料 | 各 scope 完整 `.dustkeeper/`，包括 objects、manifests、tmp、owner、anchor |
| 旧程序 | 旧二进制、版本和摘要 |

`pause` 不替代停止调度，也不代表进程立刻退出。系统自带 SQLite 版本可能不支持现有表定义，不把系统 `sqlite3 .backup` 写成通用步骤。

**状态库副本不是沙箱。** 库中保存原 scope 的绝对路径；对副本执行 `run/restore` 仍可能改变原目录。受控演练使用独立测试目录和独立实例，不直接运行生产状态库副本。

### 5.3 升级与核对

在目标账号下，明确指定同一实例的配置与状态目录，再调用已核验的新二进制。下面是模板，必须先替换路径：

```sh
export DUSTKEEPER_CONFIG_DIR=/absolute/confirmed/config
export DUSTKEEPER_STATE_DIR=/absolute/confirmed/state
DK_BIN=/absolute/final/path/dustkeeper

"$DK_BIN" version
"$DK_BIN" init
"$DK_BIN" status --json
"$DK_BIN" scope list --json
"$DK_BIN" review unknown list --json
```

明确规则：

- 只支持已知 schema 3/4 经显式 `init` 升到 5；普通 `status/run` 不会帮忙迁移。
- 非空 journal/WAL 先保留现场，用旧二进制完成恢复并正常关闭，再升级。不得删除 sidecar、改版本号或重建库绕过核对。
- 升级后核对实例 ID、scope、授权、保护、对象、pending 与未知请求记录是否保留。不要只看 `init` 退出 0。
- 升级过程本身不调用模型、不移动对象、不自动启用调度。
- 先完成核对，再考虑清除全局暂停；`resume` 只清全局暂停标记，不恢复 scope 状态或补发授权。

旧配置不会自动得到新默认。重点核对：

| 项目 | 本轮核对要求 |
|---|---|
| `runtime.run_soft_seconds` | 既有 60 不会自动改成 300；需显式采用可容纳完整审核路径的值 |
| `timeout_seconds` / `reserve_seconds` | 核对实际值；任务与批次时间至少容纳 `2 × timeout + reserve` |
| `batch_max_attempts` | 每次启动新候选需要至少 2 个剩余尝试额度；配置 1 虽合法，但不会开始审核 |
| JEV 阈值 | 记录已批准值；90/90 是默认，70/80 是放宽，不能为了得到删除结果临时降低 |
| 凭据 / CA / 代理 | 核对目标账号实际可读；CA 使用全程无符号链接的真实路径 |
| 文件动作额度 | 沿用已批准额度；首跑可减少，不扩大范围或额度 |

### 5.4 回退边界

- **新版尚未产生新的模型请求或文件动作：** 停调度、确认无人持锁后，可以恢复同一停机点的完整旧状态与旧二进制。
- **已经产生新请求或文件动作：** 不单独把数据库退回旧备份。先暂停，保存最新状态，向前修复或对账；否则可能抹掉请求、保护或已发生动作的事实。

### 完成标准

新制品与实例对应；显式升级成功且历史状态保留；配置有效；调度仍未自动恢复；未知请求和 pending 的现状已有记录。

## 6. 第四步：一次小范围真实运行

### 6.1 运行前准备

选择业务已确认可丢弃、已有清晰授权的小范围，优先少量候选。首次真实请求使用已批准的服务、阈值和费用额度。

1. 对实际 scope 执行 `doctor --scope <scope_id>`，核对目标机能力。
2. 扫描并预览实际规则，保留候选清单和规则版本。
3. 核对整轮可能处理的旧 pending 与到期对象；`run` 的对账和清空在新扫描之前。
4. 如需重新确认规则，按原能力、原额度走 `rule enable` 的预览与 digest 两次调用。
5. 检查模型配置与实例环境；`doctor` 不包含真实模型检查。额外执行 `debug --execute` 会产生真实请求，只有明确需要时才做，不重复调用来凑证据。

`run --dry-run` 只列 pending，不扫描、不审核、不预演下一轮删除。候选预览必须使用 `scan` 和 `rule preview` 等实际入口。

使用 `retention plan` 时，其结果只是只读建议；清单引用没有绑定执行授权，修改清单不会自动使旧授权失效。先核对实际规则与当前引用，再执行。

### 6.2 只执行一次，并保留原始结果

解除本次明确允许解除的暂停后，使用最终安装路径执行一次 `run --json`，保存原始 stdout、stderr、进程退出码和本轮结果页。

本轮结果需要回答：

| 问题 | 核对方法 |
|---|---|
| 实际删除了什么？ | 已完成动作记录与文件现场对应，不能只看模型同意或 intent |
| 哪些进入待删除区？ | 对象存在、最早清空时间和恢复命令可查 |
| 哪些保留，为什么？ | 区分模型保留、预算未开始、请求未知和本地事实不足 |
| 本轮到底有没有动作？ | 同看退出码、run ID、结果页和实际现场；非零退出不代表整轮零动作 |
| 模型在哪一步停了？ | 关联 `review_id`，查看 JEV/MiniMax 请求与失败类别 |
| 有没有旧未知请求被重问？ | 先前未解决记录仍在时，同证据同动作不应增加新请求 |

不要强求真实模型在这一轮同时产生删除、隔离、保留三种结果。真实模型选择保留就接受保留；某分支未触达时，写明“该目标机本轮未观察到”，机制覆盖由同一候选的原生受控测试说明。

如果完全没有有效候选，只能证明空轮运行成功；在本次范围内补一个已批准的候选后再验证一次即可，不扩为反复批量试验。已有候选被保留，则保留就是有效结果，无需为凑动作而反复请求。

### 6.3 恢复与 F1(a)

如果本次自然产生了待删除对象，可以在获准的受控样本上验证恢复；不擅自恢复旧真实对象。恢复后核对字节与保护记录，并按原能力、原额度重新确认该 scope 的规则。

F1(a) 保持：恢复更新保护版本，旧授权可能失配。其它 scope 或先前动作仍可能已经执行，不能把 `GRANT_REQUIRED` 解读为整轮零动作。旧观察区对象不自动继承新授权。

此前 V11 的旧真实隔离对象恢复仍是单独运维事项，不作为本轮继续开发新功能的理由。

### 完成标准

一个明确范围完成一次有有效候选的真实运行，结果可解释、文件现场与记录一致，预算与未知请求行为没有未处理的阻断异常。缺少的真实分支明确登记。

## 7. 第五步：真实调度触发与有限观察

### 7.1 验证一次实际触发

从最终安装路径渲染调度配置，因为模板记录的就是当时的二进制路径。核对：

- 实际可执行路径与发布制品一致；
- 运行账号、配置目录、状态目录与手动首跑一致；
- 服务获得必要环境；凭据不写进验收文档；
- 结果页与日志输出目录正确；
- 已确认的通知 `none` 保持如实显示，不声称已主动送达用户。

安装并启用本次已批准的实际单元，等待 timer/launchd 自己触发一次。保存开始时间、结束时间、退出状态、run ID 和结果页。

手动执行与调度相同的命令，只能证明该命令可运行，不能代替真正的调度触发。调度注册失败时明确停在“手动可用”，不要记作“自动运行通过”。

### 7.2 再观察后续 3 次预定触发

这是本次建议的有限运营验收窗口，不是代码新增机制，也不是统计意义的误删率验收。

每轮检查一次：

1. 是否按预期被调度、是否发生重叠运行。
2. 本轮结果页、日志与 run ID 是否对应。
3. 实际动作、未开始、失败和待核查是否区分清楚。
4. 已有未知请求是否继续阻止自动重问。
5. 预算不足是正常分批，还是候选始终无法启动。
6. 未处理异常是否需要暂停；没有异常则按原计划继续。

首个真实调度触发加后续 3 次预定触发都留下结果后，即完成这个观察窗口。保持原有执行频率，不为赶进度临时高频运行真实模型。

若触发频率为每天一次，就按真实日历观察；执行者交接时写明尚待发生的日期，不用手工连续运行代替日历调度。

## 8. 第六步：采集数据，做一次分析与验收结论

### 8.1 每轮结束后采集

使用与二进制来自同一提交的采集脚本，输出不同文件名，避免最新结果被下一轮覆盖后失去逐轮证据：

```sh
python3 /absolute/scripts/collect-run-data.py \
  --state-dir /absolute/confirmed/state \
  --output /absolute/private/dustkeeper-run-YYYYMMDD-HHMMSS.zip
```

脚本只读取标准位置的四份 JSONL 日志和 `reports/latest.json`，附加采集清单。当前实现：

| 项目 | 行为 |
|---|---|
| 日志输入 | 当前日志与 `.1`、`.2`、`.3`，每份最多 2 MiB + 64 KiB |
| 结果页输入 | `reports/latest.json`，最多 4 MiB |
| 源文件总上限 | 约 12.25 MiB |
| 输出 | 新建 0600 ZIP，不覆盖已有文件 |
| 清单 | 采集时间、文件状态、大小、SHA-256、读取期间变化 |
| 不完整数据 | 缺失、拒绝、不可读、超限明确标记，不冒充完整 |
| 执行动作 | 不运行 Dustkeeper、不调用模型、不上传 |

自定义 `result-dir` 不在当前白名单内。使用自定义目录时，另外保留实际结果页并标注来源和 run ID；不要为了这次交接新增通用目录发现功能。

ZIP 不是一致性恢复备份，也不是供应商账本。结果页可能包含业务文件名和路径，按实际分享对象处理即可。采集期间若程序仍在运行，清单会保留可观察的变化事实，但不能保证整包属于同一时刻。

### 8.2 最小交接材料

同一私有目录下保留：

```text
acceptance.md
version.txt
release-manifest.txt
build-facts.txt
SHA256SUMS
run-<run_id>.json
run-<run_id>.stderr.txt
run-<run_id>.exit.txt
schedule-evidence.txt
dustkeeper-run-<timestamp>.zip
```

这是人工归档约定，不要求开发新的归档系统。逐轮 JSON、stderr、退出码来自真实命令；没有的字段标记缺失，不手写成成功。

### 8.3 后续分析只回答六个问题

1. **是否完成了实际清理？** 分别统计已删除、待删除、保留及对应原因；隔离不等于已经释放数据块。
2. **慢在哪里？** 分开看总轮次耗时、JEV、MiniMax、连接与响应阶段；采样少时只报样本，不做稳定分位数承诺。
3. **额度是否匹配工作量？** 看候选、尝试次数、剩余时间与 `not_started_budget`，先调整执行频率或批准额度，不直接改扫描架构。
4. **失败是否被正确处理？** 区分鉴权、供应商、传输、响应、超时、预算与本地拒绝。
5. **是否存在自动重复请求？** 关联 run/item/review ID 与未解决记录；日志缺失不等于请求没有发生。
6. **是否还需要修代码？** 只有可定位、可复现、影响使用的缺陷进入修复；否则写明转维护。

HTTP 尝试次数不证明供应商收到或计费。服务返回的 token 用量用于粗看工作量，真实费用另以供应商账单核对；缺账单时写“费用未知”。

## 9. 遇到问题时如何停止本轮扩散

| 观察到的情况 | 本轮处理 |
|---|---|
| 构建、测试或发布校验失败 | 保留失败日志，修对应问题，在新 SHA 上重新过必要门禁 |
| 升级拒绝旧库或 sidecar | 保留完整现场，用旧版恢复/检查；不删库或改版本号 |
| 401、端点、CA、代理错误 | 修复配置或运行环境；已有未知请求仍需独立核查，不自动 resolve |
| `not_started_budget`，确定未发送 | 记录本次未开始；下一轮在批准额度内继续。若始终启动不了，核对两次尝试和完整时间窗口 |
| `review_unknown` / `dispatch_pending` | 保留文件与记录；核查后决定是否显式 resolve，不循环重试凑成功 |
| `GRANT_REQUIRED` | 检查实际授权和保护版本；按原能力、原额度重新确认需要的规则 |
| 状态写入失败、对象身份异常、现场与记录不一致 | 暂停新工作，保留最新状态与日志，先定位/对账 |
| 调度失败但手动运行成功 | 仅修实际单元、环境或权限；自动运行验收保持未通过 |
| 模型保留、没有删除 | 记录理由；不为了“必须清出空间”放宽阈值或移除保护 |

不得把所有非零退出都当成“没动文件”。不要通过删除未知请求行、重建数据库、回滚到旧账或放宽门禁来清空报错。

## 10. 明确的停止开发与交付标准

### 10.1 满足以下条件即可转维护

- [ ] 本轮候选已推送、创建 PR、通过双平台原生 CI 并合并。
- [ ] 最终 main 的制品、commit、SHA-256、version 有完整对应关系。
- [ ] 一个明确范围的目标实例完成备份、显式升级和状态核对。
- [ ] 一次小范围真实运行有有效候选、结果可解释、现场与记录一致。
- [ ] 正式路径的调度至少真实触发一次，后续 3 次预定触发均有记录。
- [ ] 日志与采集材料能够回答第 8.3 节的问题。
- [ ] 没有未处理的数据状态异常、越界动作或阻断基本使用的错误。
- [ ] 验收记录准确写明未触达分支、未测指标和运行范围。

### 10.2 继续记录，不扩大为新开发任务

- 自然语言规则草稿的真实语料评测。
- 长期真实账单与模型判断质量。
- 尚未自然到期的观察区对象，其到期清空实际记录。
- 尚未获准恢复的旧真实对象。
- 未部署平台的真实机器验收。

观察期尚未结束时可以按已有证据转维护，但必须写“真实到期分支尚未发生”，不能提前勾选。维护中自然触达后补记录即可。

观察期提供恢复窗口，不会自动证明文件无用，也不包含应用异常的自动发现能力。到期清空仍须通过当次本地核验、授权与双模型审核。

### 10.3 本轮不开展的工作

不新增后台服务、模型层数、监控平台、自动上传、自动 resolve、去重支线、通用故障注入框架或目录发现系统。不继续调整恢复授权设计，不为追求形式上的全覆盖而重构扫描与发布架构。

判断是否需要改代码只有一个入口：**本轮运行或测试暴露了什么具体问题，最小修复是什么，同一条证据如何证明修好。**

## 11. 验收记录模板

执行者完成后在 `acceptance.md` 填写以下内容，未完成保留“待执行/未观察到”，不得留空后默认为通过。

| 类别 | 记录 |
|---|---|
| 源码 | PR、最终 main SHA、是否相对 abd6cfc 又有修复 |
| CI | 两平台 run/job、结果、必要的 skip 说明 |
| 制品 | target、artifact、manifest commit、binary SHA-256、version |
| 目标实例 | 主机、账号、安装路径、配置/状态目录、全部 scope 与本次范围 |
| 升级 | 旧 schema、新 schema、备份停机点、实例与历史状态核对 |
| 配置 | 实际阈值、任务/批次/请求预算、代理与通知选择；不写密钥 |
| 手动首跑 | run ID、原始退出码、有效候选与实际动作、结果页位置 |
| 调度 | 单元名、真实触发时间、退出状态、对应 run ID |
| 后续观察 | 后续 3 次预定触发各自的结果与问题 |
| 数据 | ZIP 文件名、采集缺项、实际结果目录、覆盖时间窗口 |
| 未验证 | 没有触达的真实分支、长期指标、待授权运维事项 |
| 最终结论 | 源码可发布 / 手动可运行 / 有限范围自动运行；明确选择与证据 |

建议结论格式：

> 本次使用提交 `<main SHA>`、制品 `<target / sha256>`，在 `<主机 / 账号 / 范围>` 完成显式升级和一次真实运行。
> 调度已于 `<时间>` 实际触发，后续 `<3 次记录>` 已完成。实际动作与审核、请求和状态记录一致。
> 未验证范围为 `<如实列出>`。当前 `<无未处理阻断 / 列出仍阻断项>`，结论为 `<转维护 / 停留在哪一步>`。
